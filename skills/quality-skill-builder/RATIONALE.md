# 왜 이 스킬은 이런 모양인가

**이 문서는 스킬을 실행하는 데 필요 없다.** `SKILL.md`와 `phases/*.md`의
규칙에 왜 이런 모양인지 의문이 들 때만 읽는다. 규칙이 근거로 삼는 실제
사례는 `skills/quality` → `skills/quality-docs`를 만든 세션에서 나온
것들이다.

## 실행 형태: 왜 스킬 하나인가

별도 Agent 서브타입으로 만들거나 단계별로 여러 스킬로 쪼개지 않는 이유:

- 각 Phase 끝에는 사용자 확인이 필요한 체크포인트가 있다. 자율 실행되는
  Agent로 만들어도 결국 같은 지점에서 멈추고 물어야 하므로 얻는 게 없고,
  "이 스킬들을 어떤 순서로 호출해야 하는지"를 사람이 매번 기억해야 하는
  부담만 늘어난다.
- Phase들은 순차 의존적이다(Phase 3은 Phase 1+2 산출물이, Phase 4는 Phase 3
  계획이 필요). 여러 스킬로 쪼개면 산출물을 다음 스킬에 수동으로 넘기는
  과정에서 정보가 누락되기 쉽다.
- 컨텍스트가 쌓이는 문제(Phase 1의 리서치, Phase 2의 3천 줄대 코드 추적)는
  스킬을 쪼개는 대신 "각 Phase 산출물을 즉시 파일로 저장 + 무거운 조사는
  `Agent` 도구로 위임"으로 대응한다. 파일로 이어지므로 새 세션이 중간부터
  이어갈 수 있고, 이게 곧 "긴 단일 세션" 대신 "파일로 이어지는 여러 세션"을
  전제로 한 설계다.

## Phase 2: README와 실제 코드가 어긋난 사례

블로그 스타일 가이드(`hf-blog-ko-translation-guide.md`)는 "코드 주석은 자유롭게
번역 가능"이라고 적혀 있었다. 그런데 실제 하드 게이트(`code_blocks`)는 코드블록
해시를 완전 일치시켜서 주석 한 글자만 바뀌어도 항상 막고 있었다 — 가이드
문서와 실제 도구 동작이 서로 모순된 상태였다. README 요약이나 스타일 가이드
문서만 읽고 "코드 주석은 번역해도 된다"고 판단했다면 잘못된 전제로 Phase 3을
진행했을 것이다. 그래서 Phase 2는 "코드를 직접 읽어서 확인"을 원칙으로 한다.

## Phase 2: "멀티셋 비교"를 "다수결 비교"라고 잘못 쓴 사례

harness의 하드/리뷰 게이트 비교 메커니즘(`compare_counter`/`counter_diff`)을
아키텍처 문서에 설명하면서 "다수결(multiset) 비교"라고 썼는데, `다수결`은
"과반수 투표"라는 뜻이라 실제 메커니즘(두 값 리스트를 `Counter`로 세어
빼는 것 — 가방/멀티셋 빼기)과 전혀 안 맞는 표현이었다. 사용자가 지적해서
고쳤다. 메커니즘을 정확히 이해했는지는 이런 사소해 보이는 용어 실수에서도
드러난다는 게 이 사례의 교훈이다 — Phase 2 체크포인트에 "다 쓴 뒤 스스로
용어를 재검수한다"가 있는 이유.

## Phase 2/3: config 파서가 조용히 무시하는 함정 — 두 번 걸렸다

harness는 손으로 짠 미니 YAML 파서를 쓰는데, "정해진 고정 경로만" 인식하고
나머지 키는 **에러 없이 조용히 무시**한다.

1. `gates.yml`에 `required_target_keys: []`(빈 리스트)를 써서 frontmatter
   필수 키 검사를 끄려고 했는데, 파서가 인라인 빈 리스트 문법을 지원하지
   않아 하드코딩된 기본값(`["title"]`)으로 조용히 되돌아갔다. 그 결과
   frontmatter가 없는 기술 문서가 **항상** 거짓 reject되는 심각한 버그였다.
   이건 harness 코드에 한 줄 수정(`key: []`을 실제 빈 리스트로 인식)이
   필요했고, 기존 블로그 config는 이 문법을 안 써서 블로그 쪽 동작은 전혀
   안 바뀐다는 걸 테스트로 확인한 뒤 진행했다.
2. `style_policy.yml`에 새 규칙 키(`anchor_preservation`,
   `directive_preservation` 등)를 추가했지만, 파서의 고정 경로 목록
   (`load_style_policy()`의 `if path == [...]` 조건들)에 없어서 그 규칙은
   **문서화만 되고 실제로는 한 번도 실행되지 않는** 상태로 남았다. 이건
   지금도 미해결 상태로 스타일 가이드에 명시만 해 뒀다.

교훈: 새 config 키를 추가하기 전에 "이 키를 실제로 읽는 코드가 있는가"를
먼저 확인해야 한다. 안 그러면 "설정했다고 착각하지만 실제로는 무동작인 규칙"이
계속 쌓인다.

## Phase 4: `cp`+`diff`가 `Write`보다 나은 구체적 사례

"블로그 값 그대로 재사용"이라고 말한 `eval_config.yml`도 실제로는 손으로
주석을 얹어가며 다시 썼는데, 나중에 `diff skills/quality/configs/eval_config.yml
skills/quality-docs/configs/eval_config.yml`로 확인해서야 의도한 주석 4줄
외에는 정말 안 바뀌었다는 걸 확인할 수 있었다. 결과적으로는 괜찮았지만,
"확인해서 다행히 괜찮았다"는 "처음부터 `cp`+`Edit`로 만들어서 애초에 틀릴
수 없었다"보다 신뢰도가 낮다. 그리고 `cp`는 파일 내용을 모델이 다시 생성할
필요가 없어서 토큰도 덜 쓴다 — "대부분 같은 파일"일수록 두 기준(신뢰성,
비용) 모두에서 `cp`+`diff`가 이긴다.

## Phase 4: "다 만들었다"고 생각했는데 실제로는 빠진 파일이 있었던 사례

`skills/quality-docs`를 다 만들었다고 판단한 뒤, 사용자가 "기본 파일들
다 갖춰져 있는지 체크해달라"고 요청해서 실제로 `find`로 두 스킬의 파일
트리를 비교해봤다. 그랬더니 `schemas/mqm_judge.schema.json`,
`schemas/quality_report.schema.json`이 통째로 빠져 있었다 — harness가 만드는
JSON 출력 구조를 그대로 기술하는, 문서 유형과 무관하게 거의 그대로 재사용
가능했을 파일인데 단순히 잊고 안 만들었던 것이다. "다 만든 것 같다"는 주관적
판단이고, 실제 파일 트리 diff는 객관적 증거라는 게 이 사례의 핵심이다.

## Phase 1: 저장소 안에 이미 있던 리서치를 재사용한 사례

`skills/quality-docs`를 만들 때 처음부터 웹 리서치를 시작하려 했는데,
`translation-flow/docs/hf_ko_translation_best_practice.md`라는 파일이 이미
저장소 안에 있었다 — transformers/smolagents/lerobot/diffusers/
huggingface_hub의 실제 한국어 번역 PR·이슈·리뷰 코멘트를 출처 링크와 함께
정리해 둔 문서였다. 이걸 그대로 1차 소스로 썼고, 여기에 공식 가이드
(`docs/TRANSLATING.md`)와 실제 병합된 원문↔번역 파일 비교로 살을 붙였다.
저장소를 먼저 뒤지지 않았다면 이미 있는 좋은 자료를 두고 처음부터 리서치를
다시 했을 것이다.

## Phase 1: 리서치만으로는 못 짚었던 정정

앵커/목차 조사를 마친 뒤에도, 사용자가 직접 "`_toctree.yml`은 사이드바만
관리하고, 문서 안의 목차는 헤딩 구조에서 자동 생성되는 것 아니냐"고
정정해줬다. 이건 공식 가이드 문서에도, 실제 파일 비교에서도 명시적으로
드러나지 않았던 사실이었다 — 도메인 지식을 가진 사람의 확인이 문서 리서치를
대체할 수 없다는 사례. Phase 1 체크포인트가 "산출물을 사용자에게 보여주고
확인받는다"로 끝나는 이유다.
